## 1. 目标与推荐决策

为 3x-ui 面板管理员提供 Passkey 登录：用户通过设备指纹、面容、PIN 或支持用户验证的安全密钥完成身份验证，减少输入密码和验证码的次数。

本文的“必须”是验收要求；首期按以下决策实施：

| 决策 | 首期推荐 | 原因 |
| --- | --- | --- |
| Passkey 与 TOTP 的关系 | Passkey 独立登录，要求设备用户验证；密码登录继续遵守现有 TOTP 设置 | 避免把每次 Passkey 登录变成额外输入验证码的流程 |
| 密码是否保留 | 保留，暂不支持关闭密码 | 提供设备丢失、域名变更时的恢复路径 |
| 是否输入用户名 | 不需要，使用可发现凭据 | 点击按钮后由系统选择账号和凭据 |
| 支持哪些账号 | 已存在的面板管理员账号 | 不新增注册入口，不用于代理客户端认证 |
| 首期交互 | 明确点击“使用通行密钥登录” | 自动填充与条件式 UI 留到后续 |

Passkey 作为独立方式是本方案的产品策略，并不表示所有 WebAuthn 凭据都可以替代密码和 TOTP。首期只接受可发现且通过用户验证的凭据。保留密码后，账号仍然存在原有密码登录入口，不能宣称账号已完全消除密码相关风险。

若选择“Passkey 后仍需 TOTP”，必须另设计短时、不可访问面板的待完成登录状态；验证 TOTP 后才能建立正式会话，不能先登录再由前端补验证码。

## 2. 当前系统与接入点

以下结论来自当前仓库代码，不是上游版本假设。

| 模块 | 现状 | 方案影响 |
| --- | --- | --- |
| `internal/web/controller/index.go` | `/login` 校验表单、限流、通知和写入会话；提供匿名 CSRF token | 新增 Passkey 登录接口，复用登录完成逻辑 |
| `internal/web/service/panel/user.go` | 查找本地用户；本地密码失败时可尝试 LDAP；之后校验全局 TOTP | Passkey 通过凭据定位本地用户，不调用密码校验分支 |
| `internal/database/model/model.go` | User 包含 Id、Username、Password、LoginEpoch | 新增 WebAuthn 用户映射和凭据模型 |
| `internal/web/session/session.go` | Cookie 记录用户 ID 和 LoginEpoch，每次检查时加载用户并校验 epoch | 新方式仍使用同一登录会话和失效机制 |
| `internal/web/web.go` | Gin、签名 Cookie session、可配置 basePath；Cookie Secure 当前依据面板直接 HTTPS 配置 | 仪式状态另放服务端；补足外部 HTTPS 反代配置 |
| `internal/web/middleware/security.go` | CSRF、CSP 等；API 身份可跳过 CSRF | Passkey 管理必须使用浏览器会话，不能因 API 身份跳过保护 |
| `internal/web/controller/login_limiter.go` | 当前按 IP+用户名限流，5 分钟内 5 次失败后冷却 15 分钟，有容量限制 | 免用户名登录需要额外 IP 限流和有界挑战存储 |
| `frontend/src/pages/login/LoginPage.tsx` | React 登录页；支持密码及 TOTP；经 HttpUtil 请求 | 添加独立按钮和浏览器凭据调用 |
| `frontend/src/pages/settings/SecurityTab.tsx` | 安全设置、修改账号密码、TOTP 管理 | 新增“通行密钥”子标签，包含功能配置和凭据管理 |
| `frontend/src/pages/settings/SettingsPage.tsx`、`api/queries/useAllSettings.ts` | 页面统一保存全部设置 | Passkey 配置独立保存；通用保存不能覆盖敏感配置 |
| `internal/database/db.go`、`migrate_data.go` | GORM 模型注册；SQLite 与 PostgreSQL；数据库迁移、导出 | 两种数据库都必须覆盖新模型和完整备份 |
| `main.go` | 可更新账号密码、重置 TOTP | 增加服务器侧撤销 Passkey 的恢复入口 |

现有面板的凭据修改要求旧用户名、旧密码及已启用的 TOTP。新方案不会自动赋予“刚用 Passkey 登录”替代所有现有敏感操作验证的能力。

LDAP 目前作为已有本地面板用户的密码认证后备。首期 Passkey 只绑定该本地用户；不会每次登录查询 LDAP，因此 LDAP 停用账号不等于本地 Passkey 自动失效。需要强制目录账号生命周期控制的部署，应保持 Passkey 关闭；LDAP 实时状态联动另立需求。

## 3. 首期范围

### 必须提供

- 默认关闭的部署级开关；升级后现有登录继续可用。
- 面板配置界面：开关、RP ID、允许访问地址、HTTPS 部署方式和可信代理设置，支持校验及独立保存，不要求用户编辑数据库。
- 登录页“使用通行密钥登录”按钮，免用户名登录。
- 安全设置中查看、新增、重命名、删除自己的 Passkey。
- 每个用户最多 10 个有效凭据；支持平台认证器、同步 Passkey，以及具备可发现凭据和用户验证能力的安全密钥。
- 名称长度 1–64 个字符，去除首尾空白；输出按文本处理。
- 名称、创建时间、最近使用时间；最近使用未发生时显示“尚未使用”。设备名称由用户填写，不承诺识别真实设备型号或同步平台。
- 服务端验证、限流、登录结果审计、设备丢失恢复、SQLite/PostgreSQL 迁移。
- 自定义 basePath、直接 HTTPS、可信 HTTPS 反向代理的使用说明。

### 首期不包含

- 关闭密码或强制所有管理员使用 Passkey。
- 新用户注册、邀请、多角色权限体系、代理客户端 Passkey。
- 自动填充/conditional mediation、跨站 iframe、跨域 Related Origin Requests。
- 企业认证器证明策略、厂商白名单、网站自建扫码跨设备登录协议。
- 新建恢复码系统、LDAP 状态同步策略、多实例共享挑战服务。

跨设备验证可由浏览器/系统自身提供；验收以实际支持的平台为准，面板不生成独立配对二维码。

## 4. 用户流程

### 4.1 启用功能

管理员在安全设置中配置“允许 Passkey 登录”、RP ID 和允许的外部 Origin。保存或关闭此功能须使用当前账号密码和已启用的 TOTP 再次验证。首次启用也必须满足外部地址配置校验。

界面示例：访问 `https://panel.example.com:8443/secret/` 时，RP ID 为 `panel.example.com`，Origin 为 `https://panel.example.com:8443`。basePath 不属于 RP ID 或 Origin。

启用前提示：凭据绑定于站点域名；保留恢复密码；建议添加备用设备。不能从匿名请求的 Host 自动生成并保存可信配置。

### 4.1.1 配置界面位置与布局

在现有“设置 → 安全”内部新增“通行密钥”子标签，沿用 Ant Design、SettingListItem、现有主题与移动端样式。该标签始终可访问，未启用时也能完成配置。

页面从上到下展示：

1. 功能状态：未启用、已启用、配置有误；当前浏览器能否使用单独显示，不能混淆部署状态和本设备能力。
2. 登录配置：功能开关、站点域名、允许访问地址、HTTPS 部署方式及必要的反代设置。
3. 配置操作：“使用当前访问地址填入”“检查配置”“保存 Passkey 配置”“放弃修改”。
4. “我的通行密钥”：凭据列表和添加按钮；功能关闭时仍能查看、重命名和删除，添加按钮禁用并说明原因。

配置区域为整个面板生效的部署设置；凭据列表仅属于当前账号。两者使用独立加载状态，配置加载失败不显示默认值冒充已保存配置，并提供重试入口。

### 4.1.2 配置字段

| 界面标签 | 实际接口字段 | 控件与默认值 | 校验/交互 |
| --- | --- | --- | --- |
| 允许通行密钥登录 | `config.enabled` | Switch，默认关闭 | 切换仅改变草稿，保存成功才生效 |
| 站点域名（RP ID） | `config.rpId` | Input，初始为空 | 不带协议、端口、路径；匹配访问地址的确切主机名；提供 `panel.example.com` 示例 |
| 允许访问地址 | `config.origins` | 多行文本，每行一个地址，初始为空 | 每项是完整外部 Origin；仅 HTTPS；去重，禁止通配符、IP、用户信息、路径、查询、片段；开启时至少一项 |
| HTTPS 部署方式 | `config.httpsMode` | Select，默认直连；可选择反向代理 HTTPS | 直连必须存在可加载的证书和私钥，仪式请求必须实际 TLS；反代仅接受受信任来源的 HTTPS 转发头 |
| 可信代理地址 | `config.trustedProxyCIDRs` | 复用现有 `trustedProxyCIDRs`，默认回环地址 | 反代模式必须配置；校验 IPv4/IPv6 或 CIDR，拒绝全网范围；明确提示它同时影响密码登录的 IP 解析和 Secure Cookie |
| 登录验证策略 | 已确认的产品策略 | 只读说明 | 展示 Passkey/TOTP 关系及密码恢复方式；首期不增加运行时策略切换 |

配置使用独立的 `PasskeyConfig` 单例表，`Version` 与 JSON `Data` 同行原子更新；代理地址仍保存在现有公共 Web 设置 `trustedProxyCIDRs`。配置接口在同一事务中保存两者并失效会话。通用设置接口拒绝任何 `passkey*` 字段；独立配置建立后，代理变更也必须经此接口再认证。

字段旁提供中文说明，RP ID 和 Origin 不要求用户先理解协议术语。允许访问地址示例：`https://panel.example.com:8443`。站点子路径不填入该列表。

“使用当前访问地址填入”只根据当前页面 `window.location.hostname/origin` 填充草稿并标明来源，由用户检查后保存；HTTP/IP 场景显示不可用于生产的原因，不自动把它加入可信配置。不覆盖现有修改，已有草稿时先显示替换预览。

### 4.1.3 校验、保存与生效

- “检查配置”执行前端校验与服务端只读校验，返回每字段错误、规范化配置，以及当前访问地址是否会被保留；不创建凭据、不写配置、不访问用户输入的任意外部 URL。
- 浏览器能力、安全上下文和来源匹配可在页面检查；TLS 终止、代理信任及真实设备可用性须明确检查范围，不能仅凭地址文本校验展示“Passkey 登录测试成功”。
- 保存前展示变更摘要；关闭功能提示将停止 Passkey 登录，改变 RP ID 提示需在新域名重新绑定，移除当前 Origin 提示当前地址将不能使用 Passkey。
- 点击“保存 Passkey 配置”弹出当前密码/已启用 TOTP 验证。后端再次校验全部字段，原子更新配置和版本；验证失败或任一字段不合法时全部不生效。
- 保存请求携带加载时的配置版本；版本已变更返回 409，提示重新加载或检查差异，不能静默覆盖其他标签页的修改。
- 功能关闭且尚未配置时允许空 RP ID/Origin；清空正在使用的 RP 配置必须同时关闭功能。填写了部分配置时仍须校验，避免保存互相矛盾的值。
- 保存期间禁用重复提交；取消验证保留草稿；保存失败显示原因并保留输入；“放弃修改”恢复上次已保存值。
- 成功后刷新状态和配置。因安全配置变更导致会话失效时，明确提示配置已保存并返回登录页；不得将预期退出误报为保存失败。
- 开关、RP/Origin 配置应保存后即时生效。若代理信任或 Cookie 设置确实需要重启，则响应明确 `restartRequired`，界面展示“待重启生效”及沿用现有重启操作；不得将待生效状态显示为已完成。

Passkey 配置使用独立草稿和独立保存接口，不混入全局“保存全部设置”负载。后端通用设置更新对显式提交这些字段返回可识别错误，避免 UI 和直接调用接口绕过再认证；公共代理配置的任何其他修改入口也必须采用同样保护。

### 4.2 添加 Passkey

1. 已登录用户进入“设置 → 安全 → 通行密钥”，填写名称并点击添加。
2. 再次提交当前账号密码；启用 TOTP 时一并提交验证码。用户名和用户 ID 取自当前会话。
3. 服务端验证成功后产生只允许添加的短时授权，签发注册选项及仪式 ID。
4. 浏览器调用 `navigator.credentials.create()`，系统完成设备验证和凭据创建。
5. 服务端消费仪式、验证结果，在事务内再次确认用户和配置版本，保存凭据。
6. 服务端保存成功才显示添加成功并刷新列表。

首个和后续凭据都需要再次认证。首期采用密码+现有 TOTP 的统一管理验证，暂不增加“用已有 Passkey 再认证”的替代分支。Cookie 会话存在本身不足以允许添加长期登录凭据。

设备创建成功而服务端保存失败时，显示“面板未完成绑定”，允许重试，并提示设备内可能存在需手动清理的孤立凭据。

### 4.3 Passkey 登录

1. 打开登录页，点击“使用通行密钥登录”，无需填写用户名或密码。
2. 服务端返回匿名登录挑战；不返回管理员用户名、用户数量或全站凭据列表。
3. 浏览器调用 `navigator.credentials.get()`，系统选择账号并完成用户验证。
4. 服务端验证签名，联合 RP ID、credential ID、userHandle 确定所属用户，确认账号存在和凭据有效。
5. 持久化验证器状态、最近使用时间，再建立现有面板会话并跳转到 `basePath + panel/`。

仅当所有验证、数据库写入及会话保存成功后才返回登录成功、发出成功通知。不能在会话保存之前记录“已成功登录”。

密码表单始终保留；Passkey 操作不受密码表单必填或 TOTP 输入框验证阻碍。取消和超时回到可操作状态，不能清空已经输入的密码表单。

### 4.4 管理与丢失恢复

- 列表和重命名要求当前浏览器登录会话；重命名额外要求 CSRF，不要求再次输入密码。
- 删除要求会话、CSRF，以及针对该删除目标的密码/TOTP 再认证。删除仅撤销本面板接受该凭据的资格，不能保证从设备或密码管理器删除私钥。
- 删除最后一个 Passkey 允许执行，因为首期密码始终保留；确认界面明确将继续使用密码登录。
- 删除成功后递增该用户 LoginEpoch，使其全部旧浏览器会话失效，包括当前会话；跳回登录页。首期不做按设备区分会话撤销。
- 丢失设备时，通过密码+TOTP 登录并删除对应凭据；忘记密码时使用服务器本地恢复入口。
- 已增加 CLI `x-ui setting -resetPasskeys=true` 和管理脚本 `x-ui reset-passkeys`；撤销第一个管理员的全部 Passkey 并递增 LoginEpoch，旧管理授权和注册仪式无法继续使用，不打印凭据材料。

## 5. 部署与账号生命周期

### 5.1 域名、HTTPS 和代理

WebAuthn 需要安全上下文；生产方案要求可信 HTTPS 域名，裸公网 IP 与普通 HTTP 不在支持范围。域名格式限制依据 [W3C WebAuthn 标准](https://www.w3.org/TR/webauthn-3/#sctn-createCredential)，安全上下文依据 [MDN API 文档](https://developer.mozilla.org/en-US/docs/Web/API/Web_Authentication_API)。开发验证同样使用 `https://localhost` 与虚拟认证器，不启用普通 HTTP 特例。

配置字段见第 4.1 节。Origin 使用规范化后的 scheme+host+非默认端口，不包含路径、查询或片段；禁止通配符、任意父域范围、任意 Origin 回显。RP ID 使用面板确切主机名；多个 Origin 仅允许同一主机的显式端口，均要求 HTTPS。国际化域名按 IDNA 规范化，默认端口 443 省略。

反向代理的对外 HTTPS 地址与后端 HTTP 地址必须分开处理。配置明确的外部地址，并保证登录和匿名仪式 Cookie 均具有 Secure、HttpOnly 和合适的 SameSite/Path。代理转发头只接受已配置的可信代理来源；直接访问后端不能伪造转发头改变验证依据或限流 IP。

前端检查 `window.isSecureContext`、PublicKeyCredential 和 credentials API；后端独立校验配置及签名中的来源。平台认证器探测失败不等于安全密钥也不可用，不能据此隐藏所有 Passkey 入口。

### 5.2 变更行为

| 事件 | 实施行为 |
| --- | --- |
| 关闭 Passkey 功能 | 禁止注册和登录，撤销所有待处理仪式；保留凭据供重新启用。递增用户 LoginEpoch |
| RP ID 变更 | 明确提示旧凭据不可用于新 RP；保留旧 RP 记录供查看/删除，新的登录只匹配当前 RP；清理仪式并使旧会话失效 |
| Origin 允许列表变更 | 再认证后生效；版本递增、清理旧仪式、使旧会话失效。同 RP 下增加合法端口不必重新绑定 |
| HTTPS 部署方式或可信代理变更 | 再认证后保存；清理旧仪式，使旧会话失效；界面准确显示即时生效或待重启状态 |
| basePath 变更 | 凭据仍绑定同一 RP；清理仪式，重新登录并验证 Cookie 路径 |
| 通过现有接口修改账号密码或 CLI 重置账号密码 | 撤销该账号全部 Passkey，LoginEpoch 递增，要求重新绑定；页面和 CLI 明确提示该行为 |
| 仅用户名变更的未来接口 | userHandle 保持稳定；不因展示名称变化重建凭据。当前修改接口同时要求新密码 |
| TOTP 配置变更 | 复用现有 epoch 失效行为，并废弃旧管理授权/仪式；有效 Passkey 保留，仍按确认后的独立登录策略执行 |
| 删除账号 | 删除其 WebAuthn 映射和凭据，不得转移给新账号 |
| 重启面板 | 凭据持久保留；内存仪式作废，用户重新点击即可 |

密码恢复时撤销全部凭据是本方案的安全策略：不能仅更改密码，却让遗失设备继续进入面板。当前 UpdateUser 与 UpdateFirstUser 都需接入该行为；UpdateUser 写回会话时应使用同一更新事务返回的用户快照，避免使用递增前的 epoch，也不能在提交后重新加载并签发可能来自并发恢复的新 epoch。

### 5.3 备份、导入与回滚

完整数据库备份应包含新用户映射、凭据和 RP 配置；挑战与短时授权不进入备份。配置模板、节点配置等非完整账号迁移场景不得携带凭据。

完整恢复后，同 RP、同用户映射的凭据可继续工作；服务器端不会因此获得私钥。恢复旧备份可能复活后来撤销的凭据并回退计数器，必须在恢复流程和文档明确提示；怀疑泄露时在服务器本地撤销全部凭据。

数据库恢复还需轮换浏览器会话签名 secret 或采用等效的、不会被旧备份回退的会话失效手段，并清理仪式；不能只依赖旧备份中的 LoginEpoch。当前实现随机刷新会话 epoch 和配置版本，并在替换数据库前写入持久化恢复记录、暂停新请求；认证恢复失败时保持保护，重启后先恢复认证状态再开放面板。恢复记录及异常处理见 [Passkey 使用与部署](../passkey.md)。

数据库变更采用增量表，不删除原密码字段。回滚到旧程序时密码路径仍可用；不能假设旧程序再次导出数据库会保留不认识的新表，回滚前保留完整备份。

## 6. 安全与服务端设计

以下参数为本项目建议值，须在实施前固定并通过测试，不是标准强制值。

- 注册要求 `residentKey=required`、`userVerification=required`、`attestation=none`；不限制 `authenticatorAttachment`，允许平台和跨平台设备。
- 登录要求 `userVerification=required`，服务端检查 UP/UV、challenge、type、Origin、RP ID hash、签名与用户归属。禁用跨站嵌套使用。
- 随机挑战至少 32 字节；仪式 ID 随机且不可预测；TTL 为 120 秒，前端提示超时可重试。
- 仪式状态存服务端，Cookie 仅携带不透明会话绑定标识；不能把完整 WebAuthn SessionData 放进可回放的签名 Cookie 后声称“一次性”。
- 消费采用原子操作；同一 finish 请求重复提交、跨会话提交、注册挑战用于登录均不得成功。校验失败后仪式也作废。
- 状态绑定浏览器匿名会话、用途、Origin/RP 配置版本；管理仪式另绑定 user ID、LoginEpoch 和目标操作。
- 管理再认证授权建议 5 分钟内有效、单次使用且绑定具体操作；开始注册消费授权，finish 仍需校验账号和配置未变更。
- 不把客户端传入的 user ID、username、userHandle 当成身份。用存储记录与签名验证结果联合解析，不使用“第一个管理员”兜底。
- 新管理路由只接受真实浏览器 Cookie 会话，不接受 Bearer/mTLS 的 API 身份替代；每次变更必须检查 CSRF。
- 数据库保存与登录、删除并发时，最终事务再次确认凭据未撤销、用户 epoch 和配置版本未改变，避免删除后竞态重新放行。
- 登出、账号恢复和安全配置变更清除相关待处理状态；成功登录刷新 CSRF/匿名绑定，避免继承认证前状态。

匿名挑战签发建议每 IP 每分钟 20 次，每匿名会话最多 3 个活动仪式；首期每进程最多 10,000 个，定期清理超时项，容量不足返回限流/忙碌，不允许无界增长。finish 另设 IP 失败限流；识别到用户后接入现有账号限流。密码与 Passkey 的账号限流不可通过切换入口绕过；Passkey 成功不能清空匿名挑战洪泛计数。

设备取消通常只发生在前端，不记为服务端签名验证失败。服务端收到的无效、过期、重放和错误签名仍受限流；不向匿名调用者区分“凭据不存在”和“账号存在”。

签名计数器不是所有设备都递增，不能一律要求大于零。W3C 将异常计数视为风险信号；本项目建议：零计数正常接受，对非备份凭据的回退/重复非零计数拒绝本次登录并审计；备份凭据结合库返回状态记录风险，不能仅凭计数回退永久禁用。该策略须用同步凭据及并发登录验证。[标准中的计数器说明](https://www.w3.org/TR/webauthn-3/#sctn-sign-counter)。

首期建议单面板实例使用加锁、带 TTL 的内存仪式存储，不额外引入 Redis。实例重启仅影响正在进行的操作；如未来支持多实例，必须换成具备原子消费能力的共享存储，不能把轮询代理下的偶然成功视为已支持。

## 7. 数据模型与库选择

实现采用 `github.com/go-webauthn/webauthn v0.18.2` 验证协议，Go 1.27.1；依赖及校验和已写入 go.mod/go.sum，已通过本地编译和签名验证。协议依据 [W3C WebAuthn Level 3](https://www.w3.org/TR/webauthn-3/)。

该库支持 `BeginDiscoverableLogin` 与 `FinishPasskeyLogin`/`ValidatePasskeyLogin`，并要求正确持久化验证器状态。[库 API 与存储文档](https://pkg.go.dev/github.com/go-webauthn/webauthn/webauthn)。

| 新增模型 | 核心字段与约束 |
| --- | --- |
| PasskeyConfig | id=1 单例、version、JSON data；与共享可信代理设置事务保存 |
| WebAuthnUser | id、user_id、rp_id、随机 32 字节稳定 user_handle；唯一键 `(rp_id,user_id)` 和 `(rp_id,user_handle)` |
| PasskeyCredential | id、user_id、rp_id、credential_id、name、完整 credential_data、created_at、last_used_at；唯一键 `(rp_id,credential_id)` |

credential ID 和 userHandle 在索引字段使用规范的无填充 base64url 文本，避免数据库二进制类型差异；转换时验证唯一编码。名称、最近使用时间属于面板元数据，不替代协议状态。

完整 credential_data 使用带版本的序列化格式保存库凭据对象，包括公钥、AAGUID、传输方式、证明信息、flags、签名计数、备份状态、clone warning 及所用扩展数据。登录后写回库更新后的对象，不只更新最近使用时间；在 SQLite 和 PostgreSQL 都执行往返还原测试。

userHandle 在同 RP、同账号下终生稳定，所有凭据共享；不能使用会变化的用户名，也不能每次注册生成一个新 handle。并发首次注册以数据库唯一约束保证单一映射。撤销所有凭据但未删除账号时保留 handle。

持久化层防止同一个凭据转绑到其他用户；删除必须限定当前用户与记录 ID。列表只返回管理用 ID、名称、时间和必要状态，不返回公钥、完整 credential_data 或内部 userHandle。

前端建议直接封装浏览器 WebAuthn API 与 base64url 转换，优先使用可用的原生 JSON 转换方法并提供测试过的后备实现，不让基础登录依赖 Level 3 新接口是否存在。实现复杂度超出预期时再评估前端辅助库。

## 8. 接口

所有路径相对于现有 basePath；沿用 `{success,msg,obj}` 响应结构。以下路由已经实现，并同步生成 OpenAPI 文档。

| 方法与路径 | 身份要求 | 用途 |
| --- | --- | --- |
| GET `/passkey/status` | 匿名 | 返回部署是否启用/可用，不返回账号或凭据统计 |
| POST `/passkey/login/begin` | 匿名会话 + CSRF + IP 限流 | 返回 ceremonyId 与 publicKey 选项 |
| POST `/passkey/login/finish` | 同一匿名会话 + CSRF | 消费 ceremonyId 和 assertion，完成登录 |
| GET `/panel/api/setting/passkeys/config` | 浏览器会话 | 返回已保存配置、配置版本及实际生效状态 |
| POST `/panel/api/setting/passkeys/config/validate` | 浏览器会话 + CSRF | 只读校验草稿，返回字段错误和影响提示 |
| POST `/panel/api/setting/passkeys/config` | 浏览器会话 + CSRF + 当前密码/TOTP | 原子保存配置并返回生效/重启/重新登录要求 |
| GET `/panel/api/setting/passkeys` | 浏览器会话 | 返回自己的凭据列表 |
| POST `/panel/api/setting/passkeys/reauth` | 浏览器会话 + CSRF | 校验密码/TOTP，生成绑定操作的单次授权 |
| POST `/panel/api/setting/passkeys/register/begin` | 浏览器会话 + CSRF + 添加授权 | 返回注册 ceremonyId 和 publicKey 选项 |
| POST `/panel/api/setting/passkeys/register/finish` | 同一浏览器会话 + CSRF | 验证并保存新凭据 |
| POST `/panel/api/setting/passkeys/rename/:id` | 浏览器会话 + CSRF | 更新名称 |
| POST `/panel/api/setting/passkeys/delete/:id` | 浏览器会话 + CSRF + 对应删除授权 | 撤销凭据并使旧会话失效 |

管理接口前缀与当前 SettingController 的 `/panel/api/setting` 保持一致，但增加浏览器会话专用保护，不能继承通用 API 的 Bearer/mTLS 放行行为。配置保存请求建议为 `{config,expectedVersion,currentPassword,twoFactorCode}`；密码与验证码仅用于本次验证，不进入配置表、响应或日志。

配置读取与保存响应分别展示 persisted/effective 状态、版本及 restartRequired/reauthRequired；字段错误使用稳定字段路径，便于前端逐项展示。关键信息在触发会话失效前随保存成功响应返回。重新认证不能生成任意管理操作通用的、无限次使用的授权。

begin 响应为 `obj={ceremonyId,publicKey}`；finish 请求为 `{ceremonyId,credential}`。注册名称在 begin 校验并绑定服务端状态，finish 不接受更换所属用户或任意覆盖名称。

状态建议：输入错误 400、未登录 401、CSRF/来源错误 403、重复/版本冲突 409、过期 410、限流 429、服务不可用 503。认证失败文案保持泛化；错误码的最终格式与现有 HttpUtil 处理统一，不能只依赖 HTTP 200 或字符串匹配。

选项、认证响应与列表使用 `Cache-Control: no-store`。Passkey 接口设置独立请求体上限，建议 64 KiB，超过上限返回 413；attestation=none 的实际响应体大小需验证。

## 9. 界面、审计与错误处理

登录按钮仅由部署状态与当前浏览器能力决定显示/禁用，并提供无法使用的原因。状态接口失败不能使密码登录停在加载状态；浏览器不支持、普通 HTTP、无匹配凭据、取消、超时分别提供可操作提示。

浏览器的 NotAllowedError 可能包含取消、超时或无凭据等多种原因，无法区分时统一提示“未完成通行密钥验证，可重试或使用密码”，不能编造确定原因。支持键盘操作、焦点恢复、按钮 loading、防重复提交、切换登录方式时 AbortController 取消旧请求。

日志事件至少包含登录方式、验证成功后的用户 ID、受信任解析的 IP、时间、结果和服务端原因码。添加/删除/功能配置变更记录安全审计；成功登录继续接入现有 Telegram 登录通知，并标注 Passkey 方式，遵守现有开关。不记录密码、TOTP、完整认证响应、公钥材料和恢复授权。

凭据撤销不等于同步平台已移除该凭据；界面明确提示需要时到系统密码管理器清理。前后端新增文案接入现有 i18n，至少中文/英文完整，其他语言按项目惯例回退，并通过已有缺失键检查。
